# Hybrid drafting plan: prompt lookup merged into the DFlash block (Nov 3)

Rules basis (serve/RULES.md): "other drafting may only use the requests themselves: prompt lookup and n-grams from the conversation". The target's verification, the 8-token block and the 220-token requests are untouched.

## 1. Where things happen today (serve/sglang/python/sglang/srt/speculative/dflash_worker_v2.py, `DFlashWorkerV2.forward_batch_generation`)
- **Prefill branch** (extend / chunked prefill): target forward, then draft KV is filled from the target hidden states; `next_token_ids` is the first sampled token = the **bonus** of the first decode step.
- **Decode step** (one call per step, eager Python orchestration; the models inside it run as CUDA graphs):
  1. `_prepare_dflash_draft_block_unchecked` builds `block_ids` = [bonus, MASK x 7], positions, cache locs.
  2. Draft model forward (graph) -> `draft_next` [bs, 7] (in-graph sampler `_draft_sampler.out`, or the eager greedy head).
  3. **`draft_tokens = _draft_block_tokens_buf[:bs]`, `[:,0] = block_ids[:,0]` (bonus), `[:,1:] = draft_next`** (about line 2780 of the unpatched file). This buffer is the hand-off: `verify_input_ids = draft_tokens.reshape(-1)` -> `DFlashVerifyInput` -> `prepare_for_verify` -> target forward (verify graph). The grammar tree is also built from it.
  4. `_accept_block`: greedy = `argmax(logits)`; accepted drafts are the leading candidates equal to the target's argmax; `_commit_accept` returns `out_tokens` [bs, 8] (accepted drafts shifted left + new bonus at the accept boundary) and `commit_lens` = accept_len + 1.
  5. Draft KV is appended from the target hidden states of the committed inputs (independent of which tokens were drafted).
- Nothing downstream of step 3 reads `draft_next`, only the candidates, so replacing candidates in `draft_tokens` before verify is the only hook needed.

## 2. Token history available
- Per request the scheduler holds `req.full_untruncated_fill_ids` = origin_input_ids + output_ids (prompt incl. all earlier turns, since the judge's conversations are stateless chat requests whose prompt carries the history, + generated tokens) and `batch.prefix_lens` / `batch.extend_lens` for the chunk being prefilled.
- During decode (overlap scheduling) the host does NOT know the last committed tokens: `out_tokens`, `commit_lens`, `bonus` exist on the GPU only and reach the CPU one step late. A CPU lookup would be conditioned on a stale bonus (it needs the bonus as the last token of the suffix), so "CPU lookup overlapped with GPU drafting" does not work without a host sync or a one-step-stale query. **Decision: the lookup runs on the GPU.**
- Sampling: the judge's sampling params are unknown (flags give `--random-seed 1234`, nothing on temperature). Both paths stay valid: greedy verify compares candidates with the argmax; the non-greedy path (`compute_dflash_sampling_correct_drafts_and_bonus`) treats the candidate chain as deterministic proposals (accept with the target's probability of the candidate, residual sample on reject), which is exactly what a lookup candidate is. The merge is skipped when a draft-sampler q (selector / lilicorr) is in play (`_selector_sample`) or SIMULATE_ACC_LEN is set. With greedy verify the output tokens are those of the target alone, so they do not depend on the drafts (up to the usual batch-shape numerics).

## 3. Design (serve/sglang/python/sglang/srt/speculative/hybrid_draft.py)
- **History**: `hist` int32 [pool rows, context_len + 16] on the GPU (17 MB at 33 rows x 131 088; refused above 1 GiB), row = request-pool slot.
- **Prefill** (`observe_prefill`, eager): per request the tokens `fill_ids[start:prefix+extend]` go to the row with one pinned-free H2D and one index_put. `start` = prefix_len only if the slot is still owned by the same request id with exactly that many tokens written (continuing chunk); otherwise 0 (new request, slot reuse, retraction, radix / hierarchical-cache prefix hit: the prefix tokens are in fill_ids even though their KV is cached). The sampled first token is scattered at position `seq_lens` on the device.
- **Per decode step, all on the device, no host sync, CUDA-graph capturable (tested)**:
  1. `begin_step`: zero the hit flags.
  2. `merge` (2 kernels): kernel 1, grid (bs, ceil(W/1024)): for every candidate end position e < n-1 of the row (n = prefix_len + 1, the last token is the bonus) the suffix-match length (capped at 32) against the tokens ending at the bonus, packed `(len << 32) | e`, chunk maximum -> longer match wins, ties go to the most recent. Kernel 2, grid (bs): row maximum; if len >= MIN_MATCH (4) copy the c = min(7, n-1-e) tokens after the match into `draft_tokens[b, 1..c]`; position 0 (bonus) and the DFlash tokens past c are kept; write the hit flag.
  3. `record` (after verify, before the next step): write `out_tokens[b, :commit_lens[b]]` at positions prefix+1.. (the new bonus is the last one and is the next step's suffix end), and atomically add the counters.
- **Counters** (device int64, no per-step prints): request-steps with / without a lookup hit and the tokens committed in each; a non-blocking pinned snapshot + event is read every 2000 steps and one `HYBRID_DRAFT ...` log line is emitted on rank 0 (hit rate, mean tokens per step with hit / without). Mean tokens per step = accept_length (includes the bonus, as in the repo's naming).
- **Fallback**: `SGLANG_MUSE_HYBRID_DRAFT` (default on), `SGLANG_MUSE_HYBRID_MIN_MATCH` (default 4) in `Envs`; the build runs the kernels once at server start (compile at startup) and any exception at build or in a step disables the hybrid with a warning and leaves DFlash untouched (same pattern as the MK MoE / projection binds).
- **Cross-rank**: every TP rank holds the same history and runs the same deterministic integer kernels on the same synchronised accept results, so the merged draft tokens are identical on all ranks.

## 4. Tested (CHECK-only file muse_bf16_proj/hybrid_check1.py, job 3b892751442f4602, 1 of 3 allowed checks)
Kernels vs the python reference (288 rows, widths 8 208 and 131 088, 1-chunk to 129-chunk histories, boundary-straddling matches, constant / unique / periodic / tail-repeat rows): 0 mismatches; record kernel, counters, end-of-row mask; prefill writer (delta-only chunks, slot reuse, bonus placement); decode simulation on periodic text with a DFlash stand-in (45 % per-token): 1.831 -> 8.000 tokens per step, counters equal the host-recomputed ones; capture + replay of begin_step / merge / record bitwise equal to eager; merge cost 54.6 us per step at bs 32 with 60 000-token histories (graph replay).
NOT tested: anything inside a server (see PREFLIGHT_REPORT.md, hybrid section) and the real hit rate / gain on the judge's traffic: **no end-to-end number exists**; the 8.000 above is a synthetic ceiling, not an estimate.

## 5. Policy and what would change it
Start: lookup when the longest suffix match >= 4 tokens, else DFlash. Weakness: a lookup candidate overrides DFlash tokens at positions 1..c even when DFlash would have been right; a 4-token match on boilerplate (indentation, braces) can be wrong while DFlash was right. The counters (tokens/step with vs without a hit) are the only evidence available in a server run; if tokens/step on hit rows is not above the miss rows, raise MIN_MATCH (8) or merge only where the lookup is longer than DFlash's agreement. Not done: needs a real run.
